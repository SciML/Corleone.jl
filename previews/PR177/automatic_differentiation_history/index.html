    Historical AD validation#

    This archive preserves the rewrite's dated correctness checks, measurements, and implementation investigations. References to “current” or “previous” describe the checkout used for that snapshot, not necessarily today's implementation. Earlier passing results are not a compatibility guarantee. Use the current AD guide for maintained regression coverage and recommended configurations.

    This page records the configurations tested with ShootingLayer, their known limitations, and the design decisions behind differentiable trajectory assembly. Compatibility depends on both the outer differentiation backend and the sensealg used by the underlying SciML problem.

    Maintained regression groups#

    The Differentiation test group exercises full ODE solves with ForwardDiff, ReverseDiff, and Zygote against an analytic reference at two inputs. The loss includes saved states and continuity residuals; inputs include shared parameters, a free global initial value, interior shooting values, and numerical values in Lux state. ForwardDiff and Zygote cover serial and threaded layers. ReverseDiff uses serial execution with FullSpecialize and SensitivityADPassThrough().

    The Distributed group compares two-worker ForwardDiff gradients with serial execution and finite differences. It uses a named callable objective loaded on every worker; anonymous objective closures can produce mismatched ForwardDiff tag types after serialization. Reverse-mode differentiation of the ensemble map still records blocks serially. These checks do not establish compiled ReverseDiff tapes, parallel reverse execution, Mooncake, or Enzyme support.

    Run either group from the repository root:

    GROUP=Differentiation julia --project=. -e 'using Pkg; Pkg.test()'
GROUP=Distributed julia --project=. -e 'using Pkg; Pkg.test()'

    The dated measurements below remain historical snapshots rather than a fresh benchmark of the current checkout.

    Configuring the solver and backend#

    Full specialization and pass-through#

    The ReverseDiff, Mooncake, and Enzyme configurations above used the following problem construction for an in-place right-hand side rhs!:

    using SciMLBase, SciMLSensitivity

f = ODEFunction{true, SciMLBase.FullSpecialize}(rhs!)
prob = ODEProblem(f, u0, tspan, p;
    abstol = 1e-11, reltol = 1e-11,
    sensealg = SciMLSensitivity.SensitivityADPassThrough())

    Pass-through bypasses SciML's sensitivity overrides and lets the outer backend differentiate the numerical solver directly. It retains the solution object and its saved metadata. It is a different differentiation strategy from using a SciML adjoint algorithm, and the two strategies need not have the same memory or runtime behavior. See the SciML sensitivity interface.

    ForwardDiff and FiniteDiff#

    The tested DifferentiationInterface backends were DI.AutoForwardDiff() and DI.AutoFiniteDiff(; fdtype = Val(:central)), where import DifferentiationInterface as DI.

    ForwardDiff passed both control-only and shooting-state cases with the default problem configuration. The FiniteDiff backend check covered controls; central differences were also used as the independent reference for the other cases.

    ReverseDiff#

    The passing configuration used DI.AutoReverseDiff() without a compiled tape, together with full specialization and pass-through sensitivity.

    In the historical control-only check, fixed initial states were promoted inside the differentiated loss using the value-preserving expression [u + 0 * z[1] for u in prob.u0], where z is the active optimization vector. The problem was remade with those initial states before applying the layer. This makes the initial state compatible with the tracked arithmetic introduced by the controls. The shooting-state case did not need this separate promotion. The current scalar-packing implementation passes both cases without caller-side promotion.

    Default ReverseDiff sensitivity path is currently unsupported

    DiffEqBase's default ReverseDiff solve rule returns a tracked array of state values instead of the full solution object. Its implementation converts the primal solution with Array(out[1]). Consequently, .u, .t, .alg, and other solution fields are unavailable on that return value.

    Extracting the terminal matrix column and passing its boundary time to the initial-condition layer fixes the first handoff problem. The subsequent solve must also obtain its algorithm from the layer, and trajectory assembly still needs the actual saved times and state samples. Updating terminal-state extraction alone does not establish default-path support.

    Pass-through retains the full solution interface, but current tracked-array storage compatibility must also be checked; see the current validation above. For the relevant upstream conversion, see the upstream ReverseDiff extension. The historical check used DiffEqBase 7.21.4; this link tracks the upstream source.

    Zygote#

    DI.AutoZygote() passed both control-only and shooting-state cases with the default problem configuration.

    The original trajectory constructor collided with a LuxCore constructor rule that dispatched broadly on UnionAll. The layer now calls a named builder, and the public constructor has a constructor-specific configured ChainRules rule. Rules for parametric constructors should dispatch on an appropriate Type{...} signature, rather than typeof(Constructor). See the ChainRules constructor guidance.

    Trajectory gathering uses a dedicated pullback instead of relying on Zygote.Buffer. The existing segment-solver buffers still use the Zygote extension when it is loaded. Zygote's limitations documentation describes mutation restrictions and cautions about Buffer.

    Mooncake and Enzyme#

    These cases computed the segment times before differentiation and reused them while changing numerical parameters on the same grid. The benchmark used these internal entry points:

    segment_times = Corleone.get_timestops(layer, ps, st)
trajectory, next_st = layer((layer.problem, segment_times), ps, st)

    This is distinct from preparing a gradient: all backend checks used DI.prepare_gradient, while these two also prepared the segment schedule. The current layer also caches segment times in st.timestops during setup; ordinary forward calls reuse that cache. After changing schedules, refresh it with st = merge(st, (; timestops = Corleone.get_timestops(layer, nothing, st))). Gradient preparations may also need rebuilding when dimensions, types, or traced control flow change.

    Mooncake used DI.AutoMooncake() and passed the shooting-state case. An initial 180-second worker limit was too short and was inconclusive. The full-trajectory follow-up passed in approximately 290 seconds with a 900-second limit, including package loading, compilation, and validation. These worker times are not warmed gradient timings. In a separate run without trajectory construction, preparation alone took approximately 158 seconds.

    Enzyme used the following backend and passed the control-only case:

    using Enzyme
import DifferentiationInterface as DI

backend = DI.AutoEnzyme(;
    mode = Enzyme.set_runtime_activity(Enzyme.Forward),
    function_annotation = Enzyme.Const)

    The original trajectory construction raised an IllegalTypeAnalysisException. Resolving the symbolic container once at layer construction and retaining its concrete type removed that failure in the tested configuration. Runtime activity was already enabled; enabling it alone was not the fix. See the Enzyme FAQ for activity and memory-layout requirements.

    Trajectory differentiation contract#

    The trajectory retains layer, ps, and st by reference. Saved state arrays are also shared with the segment solutions. Parameter histories are evaluated through layer.parameter and the retained ps/st; no separate parameter-history struct or detached copy is stored. Mutating these objects changes later parameter queries, so they must not be mutated between a forward evaluation and its pullback.

    Assembly separates fixed-grid layout metadata from numerical state gathering. The gathering pullback accumulates contributions into source samples, including when an index occurs more than once. State values, residuals, and parameter values remain differentiable. Symbolic metadata and the discrete layout are excluded from the ChainRules differentiation path.

    Validation covers numerical gradients on fixed time grids. It does not establish gradients with respect to event times, control-knot positions, or changes in grid topology. The full-solver matrix covers ODEs; it does not establish DAE, SDE, GPU, or higher-order derivative support.

    Preserving metadata for array-returning solve rules#

    Actual saved times cannot generally be reconstructed from the outer control grid or segment boundaries. saveat, callbacks, and other saving settings can affect the samples saved by the solver. Internal tstops affect integration and need not each appear as a saved sample. States and timestamps must correspond to the same actual solve. DAE derivative values may need preserving as well.

    If support for the default ReverseDiff sensitivity path becomes necessary, the adapter belongs at the segment-solve boundary. It should perform one primal solve, preserve that solve's actual metadata before array conversion, expose differentiable numerical values, and connect those values to the solve pullback. Metadata must remain consistent on subsequent evaluations and tape replay. An extra solve solely to recover timestamps is not the intended design.

    This adapter is deferred until a workload requires the array-returning adjoint path. Prefer documenting the working configuration over maintaining a custom solver differentiation rule without that requirement.

    Forward-pass measurements#

    The AD refactor was also compared with the preceding trajectory assembly on a 120-interval Lotka problem. Five rounds of 5,000 samples used one Julia thread; these are warmed forward timings with no gradient evaluation.

    Mode Trajectory assembly Forward time Allocated bytes/call Allocations/call
    No AD backend loaded Previous 269.1 µs 865,368 17,381
    No AD backend loaded Current 256.5 µs 861,560 17,292
    Zygote loaded Previous 255.8 µs 884,704 17,385
    Zygote loaded Current 252.8 µs 879,888 17,295

    The previous assembly was reconstructed on the same current solver. In a separate assembly-only comparison with symbolic metadata cached in both versions, the old loop took 1.72 µs and the new layout/gather took 1.68 µs. The new version allocated 6,768 bytes in 21 allocations, versus 6,048 bytes in 25 allocations for the old loop. Thus the extra layout storage cost 720 bytes, with essentially equal runtime. Allocated bytes are not peak or retained memory.

    These measurements showed no full-forward regression; they do not rank backend gradient performance. Loading Zygote changes the existing solver-buffer path, so comparisons should record which optional backends are loaded.

    Regression checks and future validation#

    Run the Core test group from the repository root:

    GROUP=Core julia --project -e 'using Pkg; Pkg.test()'

    test/core/trajectory_ad.jl checks analytical gradients through the public constructor and named builder with ReverseDiff and Zygote. It covers state, residual, parameter-history, and combined losses at two inputs, continuous/reset boundaries, and repeated-source-index accumulation.

    The full backend matrix above was exploratory and is not part of the committed Core suite. To repeat or extend it, use isolated processes per backend, reconstruct the ODE/loss described above, and record the exact solver and backend configuration. Compare central differences at multiple inputs, verify reference stability, reuse gradient preparations at a second input, and check that inputs are unchanged. For new solve-boundary adapters, include interior saveat samples and callbacks and verify state/time correspondence. Record failures separately from timeouts and untested combinations.
